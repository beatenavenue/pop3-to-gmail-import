# pop3-to-gmail-import

これは [README.md](../README.md) の日本語版です。内容が食い違っている場合は英語版を正とします。

POP3 メールボックスのメールを Gmail API 経由で Gmail にインポートし、一部のメッセージは Gmail に届く前に破棄するツールです。

このリポジトリは、主に**なぜ**この作りになっているのかを記録するために存在しています。コードは小さく、一人の事情に合わせて作られています。POP3 のメールを Gmail で受け取り続ける方法を探してここに来たのであれば、コードよりも以下の考察のほうが役に立つはずです。

## おそらくあなたには必要ありません

Gmail は他アカウントからの POP3 取得を新規ユーザーに提供しておらず、既存ユーザーも 2027 年 1 月にこの機能を失います。ほとんどの人にとっては、このプロジェクトより良い選択肢があります。

- **取得元のメールサーバーで転送を設定できるなら、そうしてください。** 最初のホップ、つまり送信者からメッセージを受け取ったサーバーでの転送が、最も素性の良い方法です。この場合 Gmail は送信者の SPF レコードと元の接続を評価できます。
- **単にすべてのメッセージをインポートしたいだけなら、既存のもっと完成度の高いツールを使ってください。**
  - [gmail-importer3](https://github.com/kyokuheki/gmail-importer3) は POP3 または IMAP から Gmail API 経由でインポートします。
  - [Fetch2Gmail](https://pypi.org/project/fetch2gmail/) は IMAP からインポートし、冪等な状態管理を持ちます。
  - [Turbogmailify](https://github.com/YoRyan/turbogmailify) は IMAP からインポートし、IDLE を使ってほぼリアルタイムに配送できます。
  - InboxBridge は Web UI を備えた、自前でホストするインポーターです。

このプロジェクトに意味があるのは、取得元で転送ができず、**かつ**どこにも保存される前に一部のメッセージを落とす必要がある場合だけです。

## なぜ作ったか

作者の勤務先は POP3 のみのメールサーバーを運用しています。転送はユーザー側から設定できず、管理者に頼んでも近いうちに話が進む見込みはありません。メールボックスは小さくすぐいっぱいになるので、取得のたびに空にする必要があります。

このアドレスは営業部門のメーリングリストにも登録されています。そのリストに流れるメールには、顧客データを含む表計算ファイルのように、作者が持っておくべきでない添付ファイルがしばしば付いています。作者にとって使い道はなく、必要になれば部門に直接聞けます。Gmail のフィルタで削除することもできますが、削除したメールは 30 日間ゴミ箱に残ります。目的は、そもそも一切保存しないことです。

したがって要件はこうなります。

- 実行のたびに POP3 メールボックスを空にする。
- デスクトップとスマートフォンの両方で Gmail からメールを読み、Gmail のスパムフィルタに頼る。
- To または Cc にリストのアドレスがあり、**かつ**添付ファイルを持つメッセージを、Gmail に届く前に落とす。

## 設計上の判断

### insert や IMAP APPEND ではなく import

Gmail のメールボックスにメッセージを入れる方法はいくつかあります。Gmail API のメソッド `users.messages.import` は、SMTP で受信したときと同様に、標準の配送スキャンと分類を通してメッセージを処理します。`users.messages.insert` と IMAP の `APPEND` はメッセージを直接配置し、スパム判定を飛ばします。スパムフィルタリングは完全に Gmail に任せる方針なので、このプロジェクトは `import` を使います。

### SRS を使っても、SMTP 転送はしない

「まともな」転送サーバーがするように、SRS と ARC を使って SMTP で転送したくなります。しかしここでは役に立ちません。

送信者の SPF レコードと接続元 IP を評価できるのは、元の送信者からメッセージを受け取ったサーバーだけです。このツールはそのサーバーの後ろにいて POP3 で取得するので、その情報を持つことがありません。SRS を使うと、Gmail は中継側自身のドメインに対して SPF を検証することになり、それは元の送信者について何も語りません。ARC も助けになりません。中継側には封印すべき信頼できる認証結果がないからです。

SMTP 転送は新たな問題も生みます。

- スパムの多いメールボックスを中継すると、中継側の IP とドメインから送ることになり、Gmail に対する評価を損ねます。
- 家庭用回線の IP はしばしば拒否され、外向きのポート 25 は塞がれていることが一般的です。
- Amazon SES のようなサービスは検証済みのアドレスからしか送信できないので、任意の送信者のメールを中継できません。

### Gmail が失うものと保てるもの

`import` では、Gmail は SPF も元の接続元 IP も評価できません。DKIM 署名はメッセージ自身の一部なので、バイト列が変更されない限り検証可能なまま残ります。そのためこのツールは、取得したままのメッセージを渡し、アップロード前に解析して再構築することを決してしません。メディアアップロードのエンドポイントを使い、JSON の中に base64 で埋め込むのではなく、生のメッセージをそのまま送ります。

Gmail 自身の POP3 取得も最初のホップより後でメールを受け取っていたので、同様の条件下で機能していたと考えられます。ただし、import 時に Gmail が認証結果をどう評価するのかは公開されていません。スパムフィルタの品質は、頼る前に実際のスパムで確認すべきです。

### 結果を確認してから削除する

メッセージを POP3 サーバーから削除するのは、Gmail が import を確認した後、またはツールが意図的に破棄した後だけです。エラーが起きた場合、メッセージはサーバーに残り、次回の実行で再試行されます。失敗したときに起きるのは、サーバーにメールが溜まることであって、メールが失われることではありません。

取得元のメールボックスは小さいので、溜まればそれでもすぐ問題になります。ツールは失敗時に非ゼロの終了ステータスで終わり、何らかの失敗通知と組み合わせて使うことを想定しています。

### import する前にフィルタする

設定したリストのアドレスが To または Cc に現れ、かつ少なくとも 1 つの MIME パートがファイル名を持つ場合、メッセージは破棄されます。このルールでは署名欄のインライン画像も添付ファイルとして数えられます。ルールは意図的に粗くしています。重要なものは送信者に再送を頼めるので、誤検出は許容できます。

### 費用

Gmail API の通常利用は無料です。`messages.import` の呼び出し 1 回で 25 クォータ単位を消費します。プロジェクトあたりの 1 日の課金しきい値は 80,000,000 単位、ユーザーあたりの上限は毎分 6,000 単位です。メールボックス 1 つならどちらにも遠く及びません。
